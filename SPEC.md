# GetMe Migration Specification

**Status:** Authoritative analysis and rewrite blueprint
**Source:** Existing repository at audit time
**Scope:** PHP/MySQL application analysis and proposed Next.js/JavaScript + SQLite design

> This document is based strictly on the files present in the repository. Proposed rewrite decisions are labeled `[ASSUMPTION]`; facts that cannot be verified from the repository are labeled `[NEEDS CLARIFICATION]`. This document contains no migration implementation code.

## 1. Executive Summary

GetMe is a small browser-based number-guessing game. A player selects a difficulty range, enters a username, and repeatedly guesses a randomly generated number between zero and the selected maximum. The PHP application stores the active game in a PHP session, displays directional hints after each guess, and writes a completed score to a MySQL `board` table when the player guesses correctly. A scoreboard displays all stored scores.

The current application is procedural PHP with page-level request handlers and server-rendered HTML. It has no login, authorization, API layer, JavaScript application code, background processing, file uploads, email, payment, or third-party business integration. Bootstrap 4 is loaded from a CDN, and the only repository image is a favicon.

The rewrite should preserve the current game as its parity baseline while addressing the current application's input validation, SQL injection, output escaping, session lifecycle, attempt-limit, and leaderboard scalability problems. Whether those corrections are required for strict compatibility is a product decision recorded in Section 15.

### Request and data flow

```text
GET /index.php
  -> server-rendered instructions and setup form
POST /middle.php { range, username }
  -> PHP session initialized
  -> username, range, random target, and count stored in session
  -> Location: play_first_time.php
GET /play_first_time.php
  -> session values displayed; first guess form rendered
POST /play.php { user_input_number }
  -> session values read
  -> guess compared with target
  -> count incremented
  -> winning score inserted into MySQL when equal
  -> hint and scoreboard rendered as HTML
POST /play.php { user_input_number }
  -> same processing repeats
```

`play.php` includes `connection.php` before calling `session_start()`. Other pages start the PHP session directly. There is no shared application bootstrap, router, model, template engine, or service layer.

### Shared state

The PHP session is the only game-state store:

| Session key | Set in | Meaning |
|---|---|---|
| `username` | `middle.php` | Player-supplied name |
| `range` | `middle.php` | Player-supplied maximum range |
| `rn` | `middle.php` | Random target generated by `rand(0, range)` |
| `count` | `middle.php`, updated in `play.php` | Number of processed guesses |

There is no explicit session destruction on exit, win, or a new game. PHP session expiry behavior is therefore deployment-dependent `[NEEDS CLARIFICATION]`.

- Nullability and default values for every column.
- Storage engine.
- Secondary indexes and unique constraints.
- Foreign keys and actions.
- Triggers, generated columns, views, stored procedures, and events.

- Server SQL mode and timezone.
- Whether the database name and credentials in `connection.php` match the deployed database.

These items are `[NEEDS CLARIFICATION]`, not evidence that the live table lacks them.

### Raw SQL found in PHP

`play.php` constructs a winning-score insert by interpolating user-controlled values into SQL:

```sql
INSERT INTO board (username, notr, level)
VALUES ('$username', '$count', '$level')
```

It also runs:

```sql
SELECT * FROM board
```

The insert is executed only when the submitted guess equals the session target. The select runs on every rendered `play.php` response. No ORM or query builder is present. The insert is vulnerable to SQL injection through `username`; the select has no ordering, limit, filtering, or pagination.

### Relationships

No foreign keys or relationships are present in the repository. `board` is a standalone score table. The current game session is not persisted in MySQL, so there is no database relationship between an active game and a score row. There are no observed 1:1, 1:many, or many:many relationships.

## 4. Proposed SQLite Schema

This is a proposed rewrite schema, not an extraction of verified MySQL DDL.

### `scores` table

The rewrite may retain the physical table name `board` for direct migration compatibility, or use the clearer name `scores` and transform the import. The recommended logical schema is:

| Column | SQLite type | Constraints | Reason |
|---|---|---|---|
| `id` | `INTEGER` | `PRIMARY KEY` | SQLite integer primary keys provide row IDs and replace MySQL `INT AUTO_INCREMENT`; SQLite does not require MySQL's `AUTO_INCREMENT` keyword |
| `username` | `TEXT` | `NOT NULL` after migration policy is agreed | SQLite has no `VARCHAR` length enforcement; application validation must define the allowed length and characters |
| `attempts` | `INTEGER` | `NOT NULL`, positive integer recommended | Clear rewrite name for MySQL `notr`; retaining `notr` is possible if schema compatibility is prioritized |
| `level` | `TEXT` | `NOT NULL`; optional `CHECK` | Replaces `VARCHAR`; a check can enforce the four observed labels, but only after deciding whether legacy/unknown values must remain importable |

Recommended logical DDL shape, shown for design clarity only:

```sql
CREATE TABLE scores (
  id INTEGER PRIMARY KEY,
  username TEXT NOT NULL,
  attempts INTEGER NOT NULL CHECK (attempts > 0),
  level TEXT NOT NULL CHECK (level IN ('BIGGINER', 'EASY', 'MIDIUM', 'HARD'))
);
```

The exact DDL must be finalized after the live MySQL schema and migration policy are confirmed. The current UI labels contain the misspellings `BIGGINER` and `MIDIUM`; preserving them is required for strict display parity, while correcting them would require an explicit data and UI compatibility decision `[NEEDS CLARIFICATION]`.

### SQLite translation considerations

- MySQL `INT` becomes SQLite `INTEGER`; SQLite uses dynamic typing, so server-side validation remains necessary.
- MySQL `AUTO_INCREMENT` becomes `INTEGER PRIMARY KEY`. `AUTOINCREMENT` is generally unnecessary unless the product requires SQLite never to reuse deleted IDs `[ASSUMPTION]`.
- MySQL `VARCHAR` becomes `TEXT`; SQLite does not enforce the declared length.
- No MySQL `ENUM`, JSON, FULLTEXT, generated column, trigger, or timestamp feature was verified in the available evidence. No equivalent should be invented.
- No foreign keys were documented. If the final schema reveals foreign keys, enable SQLite foreign-key enforcement and map each constraint explicitly.
- Indexes for leaderboard access are not currently documented. A future index strategy depends on ordering/filter requirements `[NEEDS CLARIFICATION]`.

## 6. Authentication & Authorization Plan

### Current behavior

There is no authentication or authorization. The username is an arbitrary player-supplied string. There are no passwords, accounts, roles, admin checks, tokens, login cookies, or identity verification. Anyone who can access the application can start a game and submit a score under any name.

### Proposed rewrite

`[ASSUMPTION]` Keep anonymous play as the default product behavior to preserve scope and compatibility. Use a server-managed game session containing a random game identifier, username, selected range, target, attempt count, game status, and creation/expiry metadata. The client should receive only a signed/opaque session reference, not the target number.

Recommended session options:

- For a single-instance deployment: encrypted/signed HTTP-only cookie backed by the application, provided the framework/session library supports reliable key rotation and expiry.
- For multiple instances or durable active games: SQLite-backed session records or another shared session store. This is a deployment decision `[NEEDS CLARIFICATION]`.

Required controls for the rewrite:

- `HttpOnly`, `Secure` in production, and appropriate `SameSite` cookie settings.
- Session regeneration or equivalent protection when a new game starts.
- Expiration and explicit clear behavior for exit, win, timeout, and restart.
- CSRF protection if browser cookies authenticate mutation requests.
- Server-side authorization of every game mutation against the current session/game identifier.
- No authentication should be added silently; accounts, admin roles, and score ownership are outside the observed application scope.

## 8. Data Migration Plan

No migration script is included in this specification.

1. Obtain a consistent source snapshot and the result of `SHOW CREATE TABLE board`; record MySQL version, SQL mode, character set, collation, and timezone.
2. Export the `board` table with column names, IDs, and all rows. Prefer a transaction-consistent dump or CSV export over manually copying the visible scoreboard.
3. Profile the data: row count, nulls, empty usernames, non-standard levels, non-positive attempt counts, duplicate IDs, and maximum ID.
4. Decide whether the rewrite uses physical table `board` or logical table `scores`. Keep a deterministic column mapping: `id -> id`, `username -> username`, `notr -> attempts` if renamed, and `level -> level`.
5. Create the finalized SQLite schema after resolving nullability, length, constraint, and legacy-value decisions. Do not apply a strict `CHECK` before deciding how to handle existing non-standard values.
6. Transform MySQL values into SQLite storage types. Preserve IDs and relationships; the current repository exposes no relationships beyond the score row itself.
7. Import rows in ID order inside a transaction. Do not rely on SQLite-generated IDs when preserving historical IDs.
8. Validate source and destination row counts, ID sets, usernames, levels, attempt counts, null behavior, and highest ID. Verify the next inserted ID behavior before enabling writes.
9. Run application parity tests against a copy of the migrated database, including empty and malformed legacy values if they exist.
10. Back up the original MySQL export and generated SQLite database, document the import checksum/counts, then schedule cutover.

`[NEEDS CLARIFICATION]` No source database, credentials for a migration environment, production row count, or existing data export is present in the repository.

## 11. Business Logic Risks & Edge Cases

| Severity | Risk or edge case | Current behavior | Recommended rewrite handling |
|---|---|---|---|
| Critical | SQL injection | Username is interpolated into the winning `INSERT` | Use parameterized SQLite statements and validate input |
| High | Missing server validation | `range`, `username`, and `user_input_number` are read directly from POST | Validate type, allowed values, length, requiredness, and range on the server |
| High | Stored/reflected XSS | Username and scoreboard values are rendered without explicit escaping | Framework-escape output and reject/control unsafe names |
| High | No identity/authentication | Any visitor can use any name and create scores | Preserve anonymous mode only with clear abuse expectations; add accounts only if requested |
| High | Session values trusted | Pages assume session keys exist and do not handle missing/expired state | Validate session state and return to setup with a clear error when absent |
| Medium | SQL query errors ignored | Insert and select results are not checked | Return safe errors, log server details, and preserve user-facing state |
| Medium | Unbounded scoreboard | `SELECT * FROM board` loads every row with no order or limit | Define ordering, pagination/limit, and indexes |
| Medium | Hardcoded database credentials | `connection.php` uses `root` with an empty password | Use deployment environment configuration and least-privilege credentials during any legacy operation |
| Medium | Invalid guess values | Non-numeric, negative, and over-range values are accepted into comparisons | Reject invalid guesses before incrementing attempts; decide whether out-of-range numeric guesses are errors or hints |
| Medium | Duplicate score insertion | A user can submit again after winning; exact repeated-post behavior is not guarded | Make game status terminal and make score persistence idempotent |
| Medium | Ambiguous boundary hints | Conditions overlap at target and threshold boundaries; PHP comparison coercion affects strings | Define integer parsing and ordered, mutually exclusive boundaries; add boundary tests |
| Low | Maximum tries is not enforced | Warning appears when count is at least range, but the code still processes a guess | Decide parity versus actual terminal enforcement |
| Low | Target can be zero | `rand(0, range)` includes zero | Preserve inclusive lower bound and test zero target explicitly |
| Low | Session not cleared | Exit is only navigation; no `session_destroy()` is called | Add explicit reset/expiry behavior |
| Low | Form markup issues | Some forms contain a comma after the `action` attribute and one submit tag is malformed | Correct markup during rewrite and test browser submission |
| Low | Naming and labels | `notr`, `rn`, `BIGGINER`, and `MIDIUM` are unclear or misspelled | Preserve storage compatibility, but use clearer domain names in new code and decide display compatibility |
| Low | No logging/rate limiting | No abuse or operational visibility exists | Add structured logging and request/game mutation limits appropriate to deployment |

### Exact current hint logic

For target `rn`, submitted value `uin`, and selected maximum `range`, the source checks these branches in order:

1. `0 <= uin <= (2/3) * rn`: `You are far behind the number`.
2. `(2/3) * rn <= uin <= rn`: `You are close behind the number`.
3. `rn <= uin <= rn + ((range - rn) * (1/3))`: `You are close after the number`.
4. `rn + ((range - rn) / 3) < uin <= range`: `You are far after the number`.
5. Otherwise: `We do not know where you are`.

The equality branch `uin == rn` occurs first and wins before these hint branches. Boundaries have overlap, and the source performs PHP coercive comparisons against a POST string. The rewrite must either reproduce this exactly with documented integer semantics or define corrected boundaries.

## 13. Testing & Validation Strategy

### Current-behavior parity tests

- `GET /` renders instructions, four difficulty choices, username input, and start control.
- Valid setup posts create a game with the selected range and a target from inclusive `0..range`.
- Missing or expired session state does not produce an unhandled server error.
- First and subsequent guesses both update the attempt count as defined by the final policy.
- Guess equal to the target produces a success result and exactly one persisted score.
- Non-winning guesses produce the correct hint for every threshold boundary.
- Target values `0`, `range`, and intermediate values are covered.
- Scoreboard displays migrated and newly created records using the final ordering and pagination policy.
- Two browser sessions do not share username, target, or attempt count.
- Exit/restart clears the previous game according to the final session policy.

### Validation and security tests

- Unsupported ranges are rejected.
- Empty, oversized, and invalid-character usernames follow the final policy.
- Non-integer, negative, decimal, and over-range guesses are handled consistently.
- SQL metacharacters in username cannot alter queries.
- Rendered usernames and database values are escaped.
- Mutation requests without valid session/CSRF context are rejected where cookie sessions are used.
- Repeated win submission cannot create duplicate scores.
- Attempt-limit behavior is enforced if selected.
- Database failures produce safe responses and server logs.
- Leaderboard queries remain bounded under a large fixture.

### Migration validation

Compare source and SQLite row counts, IDs, names, attempt counts, level values, null handling, and representative scoreboard output. Retain export/import checksums and a rollback backup until cutover validation is complete.

## 14. Phased Migration Roadmap

1. **Evidence and behavior freeze**: obtain live DDL/data export; confirm parity versus correction decisions; capture representative game flows.
2. **Domain contract**: finalize range/level constants, integer parsing, hint boundaries, attempt policy, score ordering, session lifecycle, and validation rules.
3. **SQLite data layer**: finalize schema, repository interfaces, parameterized queries, indexes, error handling, and migration dry run.
4. **Game state and mutation flow**: implement session/game creation, guess processing, terminal win state, score persistence, restart, and expiry.
5. **Next.js pages and components**: implement setup and game pages, status states, scoreboard, favicon, responsive layout, and pending/error states.
6. **Security and operations**: configure secrets, cookie policy, CSRF protection where needed, validation, output escaping, logging, rate limits, and database backup handling.
7. **Data migration rehearsal**: import a production-like snapshot, run parity and integrity tests, and document row-count/ID validation.
8. **Cutover**: freeze legacy writes, perform final export/import, verify application health and representative scores, then enable the Next.js application.
9. **Post-cutover review**: monitor errors, game completion rate, score writes, database growth, and abuse signals; retain rollback capability for the agreed period.

Dependencies: the SQLite schema depends on live DDL and data profiling; game API behavior depends on the parity/correction decision; cutover depends on a successful migration rehearsal and deployment/session-storage choice.
